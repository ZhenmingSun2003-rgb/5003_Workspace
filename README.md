## 一、项目简介

这个仓库用于完成 **STAT5003 Assignment 2（A2）** 的模型实现与实验分析。

我们已经把 **Assignment 1（A1）的最终提交报告** 和 **清理好的 WVS Wave 7 数据集**放进了仓库，方便大家直接参考、复用，不必重新寻找数据或重复完成 A1 的准备工作。

A2 阶段主要基于 A1 报告最后的 **Model Plan** 开展后续实验：根据各自负责的模型完成实验设计、特征处理、模型训练与调参、性能评估以及结果解释。具体实验内容以课程 A2 要求和小组讨论确定的安排为准。

**最重要的协作原则：每个人只需要维护自己负责的模型 `.Rmd` 文件；共享数据和其他人的文件尽量不要动。**

## 三、各自负责的模型怎么做

请直接在**自己负责的 `.Rmd` 文件**中完成这一模型所需要的工作，例如：

1. 说明实验目标、建模思路与选择这一模型的理由；
2. 读取共享 CSV，进行该模型需要的特征选择、编码、标准化或其他预处理；
3. 划分训练／验证数据，训练模型并设计合理的实验对比；
4. 在适用的情况下开展交叉验证（Cross-Validation）和超参数调优；
5. 输出合适的性能指标、图表和结果解释，并与 Baseline 进行比较。

**为了避免影响其他组员，请特别注意：**

- **模型专属的处理逻辑直接写在自己的 Rmd 里。** 例如，SVM 需要标准化、树模型需要尝试不同的特征组合，这些都不需要修改原始 CSV。
- 尽量通过 R 代码在内存中完成数据变换；如确实需要临时文件，请放在本地并避免将其提交到仓库。
- 使用**相对路径**读取仓库里的共享数据，例如 `read.csv("WVS_Wave7_cleaned_for_modelling.csv")`，不要写自己电脑的绝对路径。
- 为随机过程设置 `set.seed()`，并在 Rmd 中记录关键参数、软件包和实验步骤，方便复现。
- 为了让最终对比有意义，大家应尽量遵循已讨论好的数据划分、实验口径和评估指标；如需改变公共比较标准，请先在群里讨论。
- 如果发现共享数据、Baseline 或其他公共设计存在问题，**先提出问题，再统一决定是否修改**，不要自行改动公共文件。

`baseline.Rmd` 是对照用的公共参考，不要求大家把自己模型的所有代码都写进去；**模型训练与实验设计仍然以各自的 Rmd 为主**。

## 四、Git 协作方式：直接使用 main

我们目前采用比较简单的协作方式：**大家都在现有的 `main` 分支上更新自己负责的文件**。

不需要额外创建 `dev`、`feature` 分支，也不要求为了日常模型更新创建 Pull Request。因为各模型文件已经相互独立，只要注意提交范围，正常情况下不会频繁冲突。

### 每次开发与提交的推荐流程

**1. 开始新一轮工作前，先同步最新版本**（前提是本地没有尚未保存的修改）：

```bash
git switch main
git pull --ff-only origin main
```

**2. 在自己的 Rmd 中修改、运行并检查实验。**

**3. 提交前先检查哪些文件被改动了：**

```bash
git status
```

**4. 只添加自己负责的文件，然后 Commit。** 下面以 XGBoost 为例：

```bash
git add 04_XGBoost.Rmd
git commit -m "feat(xgboost): 完成初步训练与参数实验"
```

**5. 推送前再同步一次其他组员的最新提交，然后 Push：**

```bash
git pull --rebase origin main
git push origin main
```

如果其他组员刚好先推送了新版本，先拉取并整合他们的提交，再推送自己的即可。若出现冲突或 Git 报错，**先停止操作，在群里讨论或确认冲突内容**；不要通过强制覆盖远程仓库来解决。

### 几个简单但重要的约定

- **只提交自己负责的文件。** 推荐 `git add 文件名`，不要习惯性使用 `git add .` 或 `git add -A`，以免把无关改动一起提交。
- **小步提交。** 完成一个相对完整的功能、实验或修复后就可以 Commit，不必一直等到整个模型做完。
- **提交信息写清楚改了什么。** 例如 `feat(svm): 增加参数搜索`、`fix(tree): 修复缺失值处理`、`test(rf): 比较不同特征集合`。
- **不要随便改其他组员的 Rmd。** 如果需要互相帮助或调整分工，先在群里确认。
- **不要随意提交 Rmd 运行生成的大量 HTML、图片、缓存或临时数据。** 如确实需要共享实验结果，可以先讨论放在哪里。
- **不要使用 `git push --force`、`git reset --hard` 等可能丢失或覆盖他人工作的命令来处理冲突。** 如需恢复版本，先与组员沟通。

## 五、关于 CSV、Git LFS 和 .gitattributes

`WVS_Wave7_cleaned_for_modelling.csv` 文件比较大，因此我通过 **Git LFS（Git Large File Storage）** 上传了数据集。

简单理解：

- **CSV 的实际文件内容**由 Git LFS 存储，普通 Git 历史记录中保存的是指向该版本文件的指针，而不是每次都直接存储完整大文件。
- **`.gitattributes`** 用来告诉 Git：哪些文件需要通过 Git LFS 追踪。它是追踪规则配置文件，**不是用来单独管理 CSV 生命周期的文件**。
- 大家正常克隆仓库并配置好 Git LFS 后，就可以像使用普通 CSV 一样读取数据，**不需要自己上传或维护一份新的数据集**。

如本地还没有配置 Git LFS，请先安装 Git LFS，并在仓库中运行：

```bash
git lfs install
git lfs pull
```

> **请尽量不要修改、删除、重命名或重新提交 CSV，也不要修改 `.gitattributes`。** 这两个文件是全组共享的基础设施。一旦需要更换数据版本，请先由组内统一讨论和处理，以免大家使用了不同版本的数据。

## 六、实验结果如何保持可比

大家可以自由探索自己负责的模型，但为了后续整理 A2 的整体分析，请尽量做到：

- **同一数据基础：** 默认使用仓库中提供的清理后数据，不自行替换成不同版本。
- **清楚说明实验差异：** 如果某个模型使用了特殊编码、采样、特征选择或类别权重，直接在自己的 Rmd 中记录为什么这样做。
- **尽量统一比较口径：** 按照 A1 Model Plan 和组内讨论使用合理的训练／测试划分及评估方式。特别注意多分类任务中的类别不平衡，不要只凭单一的 Accuracy 下结论。
- **确保代码可复现：** 提交的 Rmd 应尽量能由其他组员从头运行，且不依赖个人电脑中的路径或未共享文件。

最终整合报告时，再统一比较各模型的表现、优缺点及实验发现。现阶段大家可以优先专注于**把自己负责的模型实验做完整、做清楚**。

---

**一句话总结：各做各的 Rmd，共用同一份 CSV 和 Baseline；开发前先 Pull，提交时只 Add 自己的文件，Push 前再同步。公共文件的任何改动，提前在组里说一声。**
